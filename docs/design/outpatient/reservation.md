# 患者予約

- 親Issue: #64
- 画面URL: `/reservations/new?patient_id=<患者ID>`

## 目的と範囲

患者に対し、診察枠または設備枠の空きを週間表示で確認し、複数の予約をまとめて登録する。枠の定員は枠・日時ごとに共有する。診療科は必須、担当医は任意とし、受付時に担当医を確定する。

診察と設備の時間的な重複を禁止・案内しない。設備予約は診察予約より先に追加でき、予約内容内で後から診察予約との紐付けを変更できる。予約変更・取消は本Issueの対象外だが、登録済み予約を独立ペインに表示し、後続画面の入口を置く。

## 画面と操作

承認済みモック: [予約画面](mocks/reservation.html)。外来一覧の「予約」→患者検索→患者選択から同じ業務ダイアログ内で開く。

1. 予約枠は「診察」「設備」のグループで複数選択し、表示文言は枠マスタ名のみとする。枠名の一意性はバリデーションしない。
2. 表示週、前週、次週は空き時間ペインで共通に操作する。選択済み枠はタブで切り替え、各枠の残数を週間表示する。
3. 空き時間を選ぶと小ダイアログを開く。診察枠では診療科・任意の担当医、設備枠では診療科・任意の担当医と、予約内容に存在する診察予約への任意の紐付け先を指定する。紐付ける場合は診療科・担当医を診察予約から継承する。
4. 小ダイアログの「確定」は予約内容へ追加するだけで保存しない。右下の「登録」で確認後に一括保存する。
5. 予約内容と登録済み予約は独立したペインで表示する。内容があふれる場合は各ペイン内をスクロールする。

週間表は横に月曜〜日曜、縦に開始時刻を配置する。週操作は空き時間見出しの下、選択枠タブはその下に置く。適用外は「—」、定員到達は「満員」、画面内に追加済みの日時は「選択済」とする。週変更の通信中・失敗時に前週の空きは表示しない。

各ペインの見出しと最下部の「登録／閉じる」は固定し、右列は予約内容と登録済み予約で高さを等分する。設備の「変更」は未保存内容の紐付け直しであり、登録済み予約の変更は対象外。紐付け先診察を取り除くと設備は独立予約として残し、診療科・医師を保持する。未保存内容を残して閉じる場合は破棄確認を表示する。

実画面の回帰検証は `e2e/reservation-layout.spec.js` で、30枠・登録済み20件・24時間行を表示し、スクロール範囲と設備先行の紐付け変更、登録確認を確認する。

## API連携

| HTTP method / URL | Request（主要条件・項目） | Response（主要データ） | 主なエラーと画面の扱い |
| --- | --- | --- | --- |
| GET `/api/patients/:id/reservation_booking` | path: integer患者ID | 200: `patient`, 有効な`reservation_slots`, `departments`, `doctor_users`, 登録済み`appointments` | 404: 患者なしを表示 |
| GET `/api/reservation_slots/:id/availability?week_start=YYYY-MM-DD` | path: integer枠ID、query: 月曜のISO date | 200: `times[]`（ISO datetime、integerの定員/予約数/残数） | 400: 月曜形式を案内、404: 枠なしを表示 |
| POST `/api/appointments/bulk` | JSON `reservation`: integer `patient_id`、`entries[]`（string `entry_key`, integer枠/科ID、ISO datetime、任意integer医師ID、任意string親キー） | 201: 登録した`appointments[]` | 403: CSRF、422: 入力/関連不整合、409: 定員競合。内容を保持し空きを再確認 |

一括登録のrequest例（親キーで診察と設備の関係を表す）：

```json
{
  "reservation": {
    "patient_id": 12,
    "entries": [
      {"entry_key": "visit-1", "reservation_slot_id": 3, "scheduled_at": "2026-10-05T09:00:00+09:00", "department_id": 2},
      {"entry_key": "mri-1", "reservation_slot_id": 8, "scheduled_at": "2026-10-05T10:00:00+09:00", "department_id": 2, "parent_entry_key": "visit-1"}
    ]
  }
}
```

書込APIは`GET /api/csrf`でtokenを取得し`X-CSRF-Token`で送る。画面内の設備親キーは同じrequest内の診察予約を指す。サーバは画面上の確定順に依存せず関連を保存する。

## 保存時の整合性

- 枠の有効状態、適用期間、曜日、時間帯・間隔、診療科、医師の有効性と診療科適合を検証する。
- 同じ送信内の同一枠・同一日時は1件に制限する。患者間の同時予約は枠定員の範囲で許可する。
- 枠ID順にロックして、枠・日時の利用数をトランザクション内で再検証・加算する。いずれかが失敗した場合、予約・利用数とも保存しない。
- SQLiteでは先頭の枠マスタの版更新で書込み権を確保してから検証する（SELECT FOR UPDATEに依存しない）。版更新は編集中の枠マスタとの競合も検出する。予約数はreserved実績から再集計し、取消済みを除外、受付済みを含む。同じ患者・枠・日時の再登録は409。ロック待ち失敗も409で内容を保持する。
- 設備が診察に紐付く場合は、患者・診療科・予約日が同一の診察予約だけを許可する。時間順序は検証しない。
