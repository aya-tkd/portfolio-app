## 更新方針

Issue #64：[学習記録](issues/issue-64.md)。直URL起動と患者検索からの業務導線の違いを具体的に指摘した。Vue/API分担はL2を維持し、登録時のトランザクションを本人が説明した新しい根拠はないため、他観点も維持する。

Issue #16のPR修正：[学習記録](issues/issue-16.md)。共通CSSとフォームの責務分離を扱い、既存マスタとの表示差異について受入判断があった。CSS/Vueの仕組みの説明は未確認のため既存レベルを維持する。PR初回の参照追記漏れもこの修正で補完した。

Issue #85：[学習記録](issues/issue-85.md)。Web処理の境界と暗黙動作をコメントに整理したが、ユーザー自身の説明・理解を示す根拠はないため全観点の段階を維持する。

Issue #85のPRフィードバック：[学習記録](issues/issue-85.md)。ユーザーからVue/Railsのライブラリや慣習の理解はまだ薄いとの自己申告があった。理解の段階を上げる根拠ではなく説明の深さを合わせる根拠として記録し、Vue・Railsとも現状維持。今後はクラス／画面の役割を簡潔に示し、ライブラリ・フレームワークの約束事が処理を担う箇所は、実際のコード順に補足する。

Issue #38のレビュー：[学習記録](issues/issue-38.md)。予約/受付/設備の粒度と会計条件を具体化した根拠を記録した。Issue #48ではVueの親子状態、GET検索、Railsの検索経路を実装と対応付けたが、Webの各段階は現状維持。実コードの説明・理解の証拠が増えるまでは、設計承認を理由に昇格させない。

理解度は作業回数だけで更新しません。概念を自分の言葉で説明できた、類似の設計判断を自力で行えた、レビューで問題を指摘できた、より高度な質問ができた、といった根拠を残します。

説明は実際の開発で必要になったタイミングに行い、既存のC#/.NETやRDBの知識との対応関係を活用します。ただし、RubyやWebの仕組みをC#/.NETと同一視しないよう差異も説明します。
