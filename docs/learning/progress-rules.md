# 学習記録・評価規約

学習の目的は、AIが作ったWeb機能の流れを理解し、設計と受入を判断できるようになること。手入力の実装量やIssue数では評価しない。全体を一つのbeginnerラベルにせず、概念ごとに段階と根拠を示す。

## 段階

| 段階 | 観察できる理解 | 次の自然な学習機会 |
|---|---|---|
| L0 未観測 | まだ説明・理解の根拠がない | 必要な場面で実例と役割を説明する |
| L1 接点あり | 説明を受け、用語と対象ファイルに接点がある | 実際の処理をたどる |
| L2 関係を理解 | 自分の言葉で役割・関係を捉える、または具体的な境界・仕組みを問える | 別の処理で入出力・呼び出し先を確認する |
| L3 流れを説明 | 対象コードの入力→処理→結果を、主要な誤解なく説明できる | 変更の影響をレビューする |
| L4 応用・判断 | 新しい場面で選択理由や影響を説明し、問題を指摘できる | 複数の案・例外を比較する |
| L5 比較・設計 | 制約とトレードオフを比較して設計方針を立て、その妥当性を検証できる | より複雑な業務へ適用する |

これは資格や一般的な熟練度の認定ではなく、説明の深さを調整する目安。分野全体に一律のレベルを付けず、「HTTPメソッド」「Railsルーティング」など観点を分ける。L2は初歩の用語説明から、L3は処理追跡の説明から先へ進める目安であり、全観点の到達を開発の条件にしない。

## 根拠と判断

- 通常のやり取りでの言い換え、具体的な質問、設計判断、PR指摘を根拠にする。質問でも関係性を捉えたものはL2の根拠になる。質問があることを未理解の証明にしない。
- AIが説明しただけならL1。単なるOK、Issue完了、自動テスト成功はユーザーの習得証拠にしない。独力実装や試験合格を昇段の条件にしない。
- 誤解が一部あれば、理解できた観点と未確認の観点を分ける。例えばVueの役割を言い換えられても、PATCHの意味は別に評価する。訂正を説明しただけで、その訂正が定着したとは断定しない。
- 観測段階に加え、根拠の確かさ（暫定 / 確認あり）を記す。高度な質問だけでL4/L5を付けない。発言がない期間や別Issueで同じ画面を扱ったことを理由に下げない。
- ユーザーの自己評価も記録し、AIの観測と区別する。評価への指摘は根拠を再確認して修正できる。
- 評価のためにクイズ、定期テスト、抜き打ちの予測問題を出さない。ユーザーが希望した練習以外では自然な会話を使う。

## 更新トリガーと記録先

1. Issue開始時にプロファイルと直近ログを読み、今回の機能で触れる概念を選ぶ。
2. 開発中は必要な場面で説明し、会話中の根拠を集める。
3. PR作成前と各PRフィードバック対応完了前に、今回の会話を見直す。`docs/learning/issues/issue-<番号>.md`を作成・更新し、`user-technical-profile.md`の該当観点を更新する。根拠がなければログに「維持・未観測」の理由を書く。
4. セッションログに学習ログへの参照を残し、PRに評価変更または維持理由を短く記載する。同じIssueの学習ログは追記・訂正し、工程ごとにファイルを増やさない。
5. merge後の通常の後片付けでは学習ファイルを書き換えない。過去の記録漏れは、次の承認済みFB対応などで遡及評価と明示して回収する。

実行するのはIssue作業を担当するAI。バックグラウンドの監視やGitHub ActionsでのAI起動は不要。人間の受入チェックは学習評価と独立して維持する。

## Issue別ログの最小形式

- Issue・PR・関連セッションログ、通常記録か遡及評価か
- 扱った概念
- 表：観点 / 会話に表れた根拠の要約 / 前→後の段階 / 確かさ / 未確認事項
- 次の機能で自然に確認できる学習機会

公開するのは技術的根拠の短い要約だけ。私的な事情や会話全文は載せない。GitHubコメントに根拠がある場合はリンクし、チャットのみの根拠はその旨を記す。架空のコメントURLを作らない。
