# Issue-Centered Development Workflow

## 目的

このプロジェクトでは、親Issueを機能単位の開発管理の正本とします。CodexはLeadとして作業を進め、ユーザーは要求の判断、設計承認、PR受入、mergeを担当します。

ユーザーの承認は対象と範囲を伴うものとして扱い、同じ承認を毎回取り直しません。AIはPRのApprove・mergeを行いません。

## 実行権限と開始・再開

- 要求の相談はドラフト作成まで。Issue作成の依頼は、確認済みの親Issueと設計・テスト・セッションログSub-issueの作成・関連付けを含む。
- Issue作成だけでは開発を開始しない。作成Skillは親Issueを`未着手`に設定して終了し、専用ブランチ、設計・モック、実装、テスト、PRを作成しない。これらは対象番号を指定した明示的な開始依頼でのみ行う。
- 「Issue #Nを進めて」は、そのIssueの調査、専用ブランチ作成、設計・モック作成、進捗記録、既存ProjectのStatus更新、承認後の実装・検証を含む。対象外のIssue変更、GitHub設定変更、公開・デプロイへは拡張しない。
- commit・push・PR作成は依頼または既存の承認範囲を確認する。「PRまで進めて」は対象ブランチのcommit・push・PR作成を含む。承認済みなら再確認せず実施し、未承認なら差分・検証結果を揃えて最後に確認する。
- 開始・再開時は、リモート、対象Issue、3つのSub-issue、PR、Gitの差分、設計承認の対象版を確認する。同じIssueやPRを重複作成しない。書き込みがタイムアウトした場合も、実際に作成されたか確認してから再試行する。
- Issue開発では最新の取得済み`origin/main`を基点に`issue/<番号>-<短い目的>`などの専用ブランチを作る。既存の対象ブランチがあれば再利用する。他の未コミット変更は破棄・混入させず、必要なら分離する。`main`へ直接pushしない。
- Sub-issueは本文リンクだけでなくGitHubの親子関係として関連付け、結果を確認する。Projectや権限が未設定なら未反映を記録し、設定を独断で作らない。ローカルでできる調査・設計は続ける。
- 再開に必要な情報（ブランチ・commit、設計版と承認、検証状況、未解決事項、次の作業）をセッションログに残す。GitHubへ記録できない場合は`tmp/`へ一時保存し、未同期を報告する。

## 親Issue

親Issueには、目的、要求の要約、受入条件、対象外、関連する業務フロー、判断済み事項、Sub-issue、PRを記録します。Issueは機能単位で作成し、`area:`ラベルで業務領域を分類します。

UI機能は原則として画面・操作単位にする。一覧・検索と登録・編集は別Issueとし、共通フォームを使う登録・編集は同じIssueでよい。「患者マスタ一式」のように独立した画面をまとめない。初回の基盤整備は、その画面を動かす最小限の範囲と依存関係を明記する。

受入条件には`AC-01`などの識別子を付け、設計・テストから参照します。確定事項にはユーザー判断の根拠を添え、AI提案・未決事項は別欄に置きます。最初の機能に必要な環境構築も範囲として明記し、未合意の技術を暗黙採用しません。

例：`area: reservation`、`area: reception`、`area: queue`、`area: billing`、`area: administration`、`area: platform`

## Project StatusとIssueの状態

親Issueの進捗はGitHub Projectsの`Status`で管理します。

| Status | Leadの主な作業 | 人間の判断 |
|---|---|---|
| 未着手 | 要求をIssueへ整理する | Issue内容の確認 |
| 設計レビュー | 設計Sub-issue、設計案、ローカルHTMLモックを準備する | 設計Sub-issueをCloseする |
| 実装 | 承認済み設計を基にコード、設計Doc、正式HTMLモックを更新する | 重要変更のみ判断 |
| 自動テスト | テストを実装・実行し、テストSub-issueへ証跡を残す | 原則不要 |
| PR承認待ち | 必要な検証を完了し、承認範囲内でPRを作成する | 受入・merge |
| 完了 | merge・Close・必要な解消確認を記録し、対象ブランチを削除してmainへ戻る | 例外・未完了事項のみ判断 |

親IssueはPRがmergeされるまでOpenとします。PR本文に`Closes #<親Issue番号>`を含め、merge時に親IssueをCloseします。

PR未作成なら`PR承認待ち`へは進めません。差し戻しは必要な段階へ戻し、設計変更は`設計レビュー`、コード修正は`実装`、再検証は`自動テスト`とします。人間のmerge後に自動Closeされなかった場合は原因を確認し、完了を偽って記録しません。

## Sub-issue

### 設計Sub-issue

設計中の議論、レビュー、Human Gateの記録です。次を含めます。

- As-Is / To-Be
- UI変更点とローカルHTMLモック
- 処理スコープ・対象外
- データのCRUD、DB・設定への影響
- 状態遷移
- テスト計画
- PdM、ドメイン、開発者の各観点によるレビュー結果
- 未決事項と判断理由

ユーザーが設計Sub-issueをCloseしたことを、設計承認のシグナルとします。LeadはClose済みであることを確認してから親Issueを`実装`へ進めます。差し戻しの場合は設計Sub-issueをOpenのままにし、設計を更新して再レビューします。

Close状態だけでなく、ユーザーによる承認目的のCloseであること、対象の設計版・モック・未決事項を確認します。取り下げや重複によるCloseは承認ではありません。設計版と承認記録へのリンクを残し、承認後の要件・UI挙動・DB契約などの重要変更は設計Sub-issueを再Openして再承認を受けます。承認内容を変えない実装上の修正は理由を記録して進めます。

設計レビュー中のHTMLモックは、ローカルの一時ディレクトリで確認します。設計承認後、正式な設計DocとHTMLモックをコードと同じPRへ含め、merge後に`docs/design/`の正本とします。

### テストSub-issue

AIが自動テストの計画、実装、実行結果を残すためのIssueです。

- 要件・設計との整合性確認
- テストケースと実行コマンド
- 実行結果と失敗時の対処
- コード品質・セキュリティ観点の確認

必要な自動テストが成功したとき、LeadはテストSub-issueをCloseできます。失敗が残る場合、親Issueを`PR承認待ち`へ進めません。

証跡にはAC識別子、テストケース・ファイル、実行コマンド、環境、対象commit（未コミットなら差分の有無）、結果を残します。未実行・失敗・対象外を区別し、コードレビューを実行済みテストの代わりにしません。PR修正で結果が古くなれば再Openし、影響範囲を再検証します。文書のみの変更など自動テストが該当しない場合は理由と代替検証を記録します。

### セッションログSub-issue

設計変更、人間からの指摘、重要な判断、PR修正、改善候補を時系列で記録します。会話の逐語録や個人情報、秘密情報は記録しません。

PR作成が成功しURLを確認した時点で、Leadが工程の成果・判断・FB反映先・テスト証跡・残る人間受入をまとめ、PRへのリンクを残してCloseする。PR作成失敗・未作成ではCloseしない。このCloseは「PR提示までの記録完了」であり、親Issueの完了・人間の受入を意味しない。

PR指摘・再検証・merge後の事実確認は、同じClose済みセッションログへ時系列コメントを追記し、記録のためだけには再Openしない。親IssueはmergeまでOpenを維持する。PR承認待ちへ進める前にログのClosed状態を読み戻して確認する。

## Leadのレビュー・パス

設計ではLeadが次の観点を順に確認し、設計Sub-issueへ結果を残します。

- PdM：利用者価値、受入条件、スコープ、対象外
- ドメイン：患者導線、外来業務フロー、医療上の判断を扱わない境界
- 開発者：実現性、UI、データ、保守性、テスト可能性

テストでは、要件追跡、設計整合性、コード品質・セキュリティ、自動テスト実行の観点を分けて確認します。独立したAgent実行が利用できる場合は、各役割に同じ設計版・受入条件と担当範囲を渡し、Leadが指摘を統合します。利用できない場合は役割別の自己レビューとして行い、独立Agentが確認したとは記録しません。

レビューには観点・指摘・根拠・修正結果・残課題を残します。賛成票の数では承認せず、重大な不整合を解消してから人間へ設計レビューを依頼します。指摘なしの場合も確認範囲を示します。

## 設計Docとモック

設計承認後、実装と同じPRで次を更新します。

- 画面・操作単位の設計Doc
- テーブル単位の設計Doc
- 画面単位の静的HTMLモック
- 設計索引

UIや処理を変更した場合は該当する設計Docを更新し、表示・操作が変わる場合にモックも更新します。保存先は[設計Doc索引](../design/INDEX.md)に従います。テーブルの物理スキーマ変更はmigrationで管理し、テーブル設計Docには業務上の意味と設計意図を残します。

## 継続的改善

ユーザーの運用見直しにより、FBはIssue Close後ではなく、要件・設計・実装・テスト・PR対応の各工程を完了する前に毎回確認する。AIが再依頼なしで必要な小改善を現在の作業単位に反映する。常駐監視・GitHub ActionsからのAI呼び出しを意味しない。

- 各工程で「指摘・失敗・手戻りを確認→再利用できるFBを分類→同じIssueブランチのSkills・Docs・テストへ反映→検証→ログ記録→次工程」の順で進める。要件整理時にまだブランチがなければドラフトに残し、実装着手前に回収する。
- 自動反映対象は、合意済みのUI/DB/説明ルールへの参照漏れ、手順の抜け、受入テンプレート、実証されたテスト観点、古い記述・リンクなど、既存の意図を保つ小さなSkills・Docs改善。根拠がない変更や既に反映済みの規約の複製は行わない。
- 一画面だけの例外はその画面設計へ残し、全画面の仕様へ一般化しない。アプリ機能の追加・設計変更、技術選定、権限・Human Gateの変更、安全制約の緩和、費用・外部サービス・GitHub設定は提案に留め、別途承認を取る。
- 根拠を同じIssueに記録し、小改善は機能変更と同じPRに含める。通常の完了処理として別の改善ブランチ・PRを自動作成しない。merge後に初めて見つかった改善は記録・提案に留め、次の承認済み作業または明示的な改善依頼で扱う。
- commit・push・PR作成は対象Issueの既存承認範囲に従う。mainへの直接push、AIによるApprove・mergeは行わない。承認済み設計や受入済み箇所に影響する変更は影響を明示し、必要な再承認・再受入を省略しない。
- 変更後は関連Skill・正本Doc・テンプレート間の矛盾とリンクを検証し、Skillsの検証を実行する。元の機能Issueを改善作業のために再Openしない。
- 各工程ログに「FB→反映先→検証」「反映不要の理由」「別途判断事項」を簡潔に残す。PR修正の完了前にも同じ確認を行い、未回収のFBをmerge後へ持ち越さない。変更不要なら無理にルールを増やさない。

初回の根拠：[Issue #1](https://github.com/aya-tkd/portfolio-app/issues/1)／[PR #5](https://github.com/aya-tkd/portfolio-app/pull/5)。画面単位の分割、AIによるローカル受入準備、実ファイルに沿う説明、テーブル命名の事前確認、スクロール時の操作性が主なFB。姓名分割・ボタン語彙・接頭辞・FE/BE構成は既存の設計正本を参照し、Skillへ仕様を複製しない。

## PRの人間受入をAIが準備する

- PR提示前に、承認されたローカル環境をAIが起動・疎通確認する。確認日時・対象commit・画面URL・再起動方法をPRに記載する。停止中・起動不可なら理由を示し、利用可能と記載しない。既存プロセスやDBを無断で停止・初期化しない。
- 設計と受入条件から、架空データによる操作手順・期待結果付きのUATチェックリストを生成する。自動テスト結果と人間の確認結果を分け、人間のチェックをAIが代行しない。
- PR修正時は本文を読み直してチェック済み項目を保ち、変更の影響を受ける項目を再確認対象として追記する。過去版のチェックを最新版の受入済みとは扱わない。
- 起動補助・DB確認など既存ツールを案内する。受入支援を理由に未依頼のツール実装や外部公開を始めない。
- PR作成成功後、セッションログを上記手順でCloseしてからPR承認待ちを報告する。親Issue用のCloses指定だけでログも閉じるとは想定しない。

## merge後の後片付け

ユーザーの継続的な依頼として、対象PRのmergeと親IssueのCloseを確認したら、対象のリモート・ローカル作業ブランチを削除し、ローカルmainへ戻る。

1. 対象PR・headブランチ・merge先・未コミット変更・ローカルとリモートの先端を確認する。単にIssueがClosedなだけ、未mergeのPR、別作業中のブランチは削除しない。
2. fetch後にmainへ切り替え、origin/mainへfast-forwardする。未コミット変更・未pushコミット・mainの分岐があれば破棄や自動stashをせず保留・報告する。
3. 対象ブランチの変更がmainへ取り込まれ、PR後の追加コミットがないことを確認する。squash/rebaseで祖先判定できない場合も自動で強制削除せず、未取り込み差分を確認して必要なら判断を求める。
4. 存在する対象リモートブランチだけを明示して削除し、ローカルは通常のbranch -dで削除する。既に削除済みならスキップする。main・他人のブランチ・別Issueの作業ブランチは対象外。
5. Closed済みログにmerge・必要な解消確認・後片付け結果を追記する。旧運用の対象ログがOpenのままなら記録してCloseし、Projectも完了へ揃える。mainの同期・差分なし・削除結果を確認して報告する。

完了処理では新しいコード・Docs・Skills差分を作らない。既存の未公開差分を見つけた場合は消さずに報告する。ブランチ削除が権限や保護設定で拒否された場合は設定を変更せず、残った対象を報告する。

## 学習とポートフォリオの成果

[AIとの協働方針](../ai/working-agreement.md)と[学習記録・評価規約](../learning/progress-rules.md)に従い、各Issueで学ぶWeb概念を1〜2点選びます。設計で短く説明し、実装後は実際のファイルとリクエスト・データの流れを示します。PR準備時と各PRフィードバック対応の完了前に会話を振り返り、Issue別学習ログと観点別の理解度・次の学習機会を更新します。理解度を測るための出題や回答待ちは行いません。

完了記録には利用者の課題、実現した動作、採用理由、検証証跡、AI担当と人間の判断を残します。READMEは現在の起動方法と実装済み範囲を正しく示し、未実装機能を完成済みと表現しません。

## READMEと現在地の更新

- Leadは毎回のPR準備とPR修正完了前に、READMEの実装範囲・画面URL・起動手順・制約を、対象ブランチのコードおよびIssue/PRと照合する。初回実装や起動手順変更時だけに限定しない。
- 機能追加・変更・廃止と同じPRでREADMEと影響する設計索引を更新する。前のIssueに関する古い記述も、この確認で修正する。
- READMEと設計索引は閲覧中ブランチの機能を説明する。「実装中」「次のIssue」など変わりやすい進捗はProject/PRへリンクし、GitHubのStatusを二重管理しない。PR上の実装を人間の受入済み・merge済みと表現しない。
- PRの検証記録に、確認した項目と修正先、または変更不要の理由を記載する。merge後は反映を確認するだけとし、通常の後片付けで更新PRを追加しない。
