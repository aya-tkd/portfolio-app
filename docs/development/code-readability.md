# コードの読みやすさと解説ルール

ユーザーの依頼によりIssue #1から適用する。Web初学者が処理を追えることと、保守しやすさを両立する。

## コード内コメント

- 新規・変更した各クラス、Vueコンポーネント、主要モジュールには、責務・呼び出し元・主な入出力を日本語で短く書く。既存コメントがこの役割を説明していれば重ねて書かず、実装とずれていれば直す。
- 主な業務処理、非同期処理のまとまり、外部から呼ばれる入口には、何を受け取り何を返すかを一行程度で示す。単純な表示整形や名前から分かる短い処理には付けない。
- Vueのtemplateが複数の業務領域・状態表示で構成され、初見では切れ目を追いにくい場合は、検索、一覧、フォーム、結果など大きな領域の先頭にHTMLコメントを置く。各タグや入力項目を逐一説明せず、画面の構成と役割が分かる範囲に留める。
- フレームワークが自動で呼ぶ処理（ライフサイクル、callback、watch、イベント、ルーティング等）では、処理が起きるタイミングと、親子・DB・HTTPなどとの関係がコードだけでは分かりにくい場合に背景を説明する。RailsやVueの全ての定型記法を逐一解説する必要はない。
- Web初学者が見落としやすい責務境界や暗黙動作（Strong Parameters、Active Recordの保存・検証、Vueの親子イベントや状態追跡等）は、実際の処理に沿って必要な分だけ補足する。一般論を貼り付けず、このコードで何を担っているかを書く。
- 制約、採用理由、副作用、失敗時の扱いを説明する。DB更新・非同期通信・セキュリティ境界を省略しない。
- コードの日本語訳だけの行単位コメントは増やさない。まず適切な命名と短い責務分割を優先する。
- 生成ファイル・lockfile・外部ライブラリはコメントのためだけに変更しない。役割は文書で説明する。
- 変更時はコメントもレビュー対象にする。クラス／画面の役割、主要な処理区切り、重要な暗黙動作が必要な範囲で説明されているか、実コードと一致しているか、古い説明や重複がないかを確かめる。未検証の保証や「完全に安全」などは残さない。

## 実装後の手ほどき

- ファイルを「画面」「通信」「サーバー」「DB」「起動・テスト」に分類し、読む順番を示す。
- 操作 → HTTP → ルート → Controller → Model → DB → JSON応答 → 画面更新の順で具体例を追う。
- `.vue`、`v-model`、`fetch`、migrationなどは初出で意味を説明する。C#/.NETとの対応は入口とし、違いも示す。
- 要点はチャット、後から参照する詳細は関連設計Docや短いガイドへ残す。手入力や試験は必須にしない。
- 解説上のFBはこの共通ルールを正本とし、各工程完了前のSkill・Doc改善は[継続的改善](issue-workflow.md#継続的改善)の承認範囲で同じPRに含める。
