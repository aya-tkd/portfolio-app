# コードの読みやすさと解説ルール

ユーザーの依頼によりIssue #1から適用する。Web初学者が処理を追えることと、保守しやすさを両立する。

## コード内コメント

- 新規・変更した各クラスに、責務・呼び出し元・主な入出力を日本語で短く書く。Vueコンポーネントと主要なJavaScriptモジュールも同様。
- フレームワークが自動で呼ぶ処理（ライフサイクル、コールバック、ルーティング）では、呼ばれるタイミングを書く。
- 制約、採用理由、副作用、失敗時の扱いを説明する。DB更新・非同期通信・セキュリティ境界を省略しない。
- コードの日本語訳だけの行単位コメントは増やさない。まず適切な命名と短い責務分割を優先する。
- 生成ファイル・lockfile・外部ライブラリはコメントのためだけに変更しない。役割は文書で説明する。
- 変更時はコメントも検証する。古い説明、未検証の保証、「完全に安全」などを残さない。

## 実装後の手ほどき

- ファイルを「画面」「通信」「サーバー」「DB」「起動・テスト」に分類し、読む順番を示す。
- 操作 → HTTP → ルート → Controller → Model → DB → JSON応答 → 画面更新の順で具体例を追う。
- `.vue`、`v-model`、`fetch`、migrationなどは初出で意味を説明する。C#/.NETとの対応は入口とし、違いも示す。
- 要点はチャット、後から参照する詳細は関連設計Docや短いガイドへ残す。手入力や試験は必須にしない。
- 解説上のFBはこの共通ルールを正本とし、各工程完了前のSkill・Doc改善は[継続的改善](issue-workflow.md#継続的改善)の承認範囲で同じPRに含める。
